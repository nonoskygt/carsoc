# S2000 Dash — Diseño

**Fecha:** 2026-08-23
**Estado:** Aprobado para planeación

## 1. Contexto

| Elemento | Valor | Verificado |
|---|---|---|
| Vehículo | Honda S2000 AP1 (2000–2003), motor F20C | Sí, por el usuario |
| Protocolo OBD-II | ISO 9141-2 (K-line) | No — se confirmará con `ATDP` en el primer arranque |
| Adaptador | Steren Bluetooth OBD-II, compatible ELM327 | No — se asume Bluetooth Clásico (SPP). Ver riesgo R1 |
| Destino | Head unit Android en el carro | Specs desconocidas. Ver riesgo R2 |
| Máquina de desarrollo | Windows 11, Node 24 / Python 3.11 / git 2.53 | Sí |
| Toolchain Android | Solo `platform-tools` (adb) en `~/Android/Sdk` | Sí — falta JDK + SDK |

## 2. Objetivo

Un **tablero en vivo para manejar**. Las dos únicas métricas de éxito son:

1. **Legibilidad de un vistazo** — se entiende sin fijar la mirada.
2. **Latencia mínima** — la aguja responde a lo que hace el motor.

Todo lo demás se sacrifica a estos dos.

## 3. No-objetivos (explícitos)

Fuera de alcance por decisión, no por olvido:

- Lectura o borrado de DTCs, freeze frame, monitores de emisiones.
- Registro de sesiones a archivo y análisis histórico.
- Cronómetros de desempeño (0–100, cuarto de milla, vuelta) y G-force.
- Datos de afinación: TPS, avance de encendido, MAF, trims de combustible.
- Unidades imperiales y selector de unidades. **Solo km/h y °C.**
- Modo demo / simulador.

Fuera de alcance por imposibilidad física en un AP1 con OBD-II estándar:

- **Temperatura de aceite, presión de aceite, posición de la marcha.** No existen como PID en ese año.
- **Señal real de enganche del VTEC.** No se puede leer; se *infiere* de RPM + carga (§7).

## 4. Restricciones duras

1. **K-line es serial y lento.** El ELM327 no admite peticiones multi-PID sobre ISO 9141-2 — eso es exclusivo de CAN. Una petición produce una respuesta, con round-trip de ~70–120 ms. Presupuesto total: **~8–14 lecturas por segundo repartidas entre todo.**
2. **El head unit tiene CPU débil** (típicamente Rockchip o Allwinner). Por eso el tacómetro se dibuja con `View` y `Canvas`, no con Compose.
3. **Los clones de ELM327 emiten basura.** `SEARCHING...`, `BUS INIT`, `STOPPED`, `?`, `UNABLE TO CONNECT`, respuestas truncadas. El parser nunca puede fallar con ninguna de ellas.
4. **Resolución de pantalla desconocida.** El layout debe escalar a cualquier tamaño horizontal (800×480, 1024×600, 1280×720) con medidas relativas al viewport, no píxeles fijos.

## 5. Presupuesto de sondeo

| PID | Dato | Cada N ciclos | Frecuencia efectiva |
|---|---|---|---|
| `010C` | RPM | 1 | ~6 Hz |
| `010D` | Velocidad | 3 | ~2 Hz |
| `0104` | Carga calculada del motor | 10 | ~0.6 Hz |
| `0105` | Temperatura de refrigerante | 20 | ~0.3 Hz |
| `010F` | Temperatura de aire de admisión | 20 | ~0.3 Hz |
| `ATRV` | Voltaje de batería | 20 | gratis — lo da el adaptador, no la ECU |

Total aproximado: 9 lecturas por segundo. `0105` y `010F` van desfasados entre sí para no coincidir en el mismo ciclo.

## 6. Arquitectura

```
SppTransport ──► Elm327Session ──► PollScheduler ──► VehicleState (StateFlow)
 (bytes RFCOMM)   (diálogo AT)      (round-robin        │
                        ▲            por prioridad)     ▼
                  PidDecoder ◄───────────────────    DashView (Canvas, 60 fps)
                  (funciones puras)                     │
                                                   DashActivity
```

### 6.1 `ObdTransport` (interfaz)

- **Qué hace:** transporta bytes. Conectar, desconectar, escribir, leer hasta el prompt `>`.
- **Cómo se usa:** `connect()`, `write(ByteArray)`, `readUntilPrompt(timeoutMs): String`.
- **De qué depende:** de nada del dominio OBD. No sabe qué es un PID.
- **Implementación:** `SppTransport`, un `BluetoothSocket` RFCOMM contra el UUID `00001101-0000-1000-8000-00805F9B34FB`.

La interfaz existe con una sola implementación real a propósito: si el Steren resulta ser BLE (riesgo R1), se añade `BleTransport` sin tocar ninguna otra unidad.

**Aclaración sobre el transporte falso.** Las pruebas de §11 usan un `FakeTransport` que reproduce respuestas guionadas. Vive **solo en las fuentes de prueba** (`src/test/`) y no se compila dentro del APK. No es el modo demo descartado en §3: no hay forma de activarlo desde la app instalada, ni genera datos plausibles de manejo — solo reproduce guiones fijos para los tests.

### 6.2 `Elm327Session`

- **Qué hace:** el diálogo AT con el adaptador.
- **Cómo se usa:** `initialize(): ProtocolInfo`, `query(pid: String): ByteArray?`, `readVoltage(): Float?`.
- **De qué depende:** de un `ObdTransport`. Nada más.

Secuencia de inicialización, en orden y con su razón:

| Comando | Razón |
|---|---|
| `ATZ` | Reset completo del adaptador a un estado conocido |
| `ATE0` | Eco apagado — no reenviar lo que mandamos, ahorra ancho de banda |
| `ATL0` | Sin saltos de línea extra |
| `ATS0` | Sin espacios en la respuesta — menos bytes sobre un enlace lento |
| `ATH0` | Sin encabezados — no se necesitan |
| `ATSP3` | Fijar ISO 9141-2 explícitamente, evita el barrido de autodetección |
| `ATAT1` | Temporización adaptativa — el adaptador ajusta su propia espera |
| `ATDP` | Reportar el protocolo activo, para registrar qué se negoció realmente |

`ATSP3` es una apuesta a que el AP1 usa ISO 9141-2. Si `ATDP` reporta otra cosa o la inicialización falla, se cae a `ATSP0` (automático) y se registra el protocolo real.

### 6.3 `PidDecoder`

- **Qué hace:** convierte bytes crudos en magnitudes físicas. Funciones puras, sin I/O, sin estado.
- **De qué depende:** de nada. Es la unidad más fácil de probar y ahí vive el grueso de las pruebas.

| Función | Fórmula |
|---|---|
| `decodeRpm` | `((A * 256) + B) / 4` |
| `decodeSpeed` | `A` (km/h directo) |
| `decodeCoolant` | `A - 40` (°C) |
| `decodeIat` | `A - 40` (°C) |
| `decodeLoad` | `A * 100 / 255` (%) |

Toda función devuelve un tipo anulable. Entrada inválida produce `null`, jamás una excepción.

### 6.4 `PollScheduler`

- **Qué hace:** ejecuta el round-robin por prioridad de §5, una consulta a la vez.
- **Cómo se usa:** `start()`, `stop()`, expone `state: StateFlow<VehicleState>`.
- **De qué depende:** de `Elm327Session` y `PidDecoder`.

Corre en una corrutina de fondo. Mide el round-trip real de cada consulta; si el enlace resulta más rápido de lo previsto, sondea más seguido sin cambios de código — el ritmo lo marca el enlace, no un temporizador fijo.

### 6.5 `VehicleState`

Data class inmutable. Cada campo lleva su propio timestamp para poder marcar valores rancios en la UI.

```
rpm: Int?              + rpmAtMs: Long
speedKmh: Int?         + speedAtMs: Long
coolantC: Int?         + coolantAtMs: Long
iatC: Int?             + iatAtMs: Long
loadPct: Int?          + loadAtMs: Long
batteryV: Float?       + batteryAtMs: Long
connection: ConnectionState
sessionMaxRpm: Int
```

Un valor con más de 3 segundos de antigüedad se dibuja en gris.

### 6.6 `DashView`

- **Qué hace:** dibuja el tablero completo en un `Canvas`.
- **De qué depende:** recibe un `VehicleState`. No conoce Bluetooth ni OBD.

Contenido:

- **Tacómetro de barrido de 0 a 9000 rpm**, elemento dominante.
  - La **zona roja** (8300+) va siempre pintada en la carátula.
  - La **banda VTEC** (5850–9000) va siempre dibujada en la carátula, tenue. Cuando `vtecActive` es verdadero, se ilumina. Es decir: la banda marca *dónde* está el VTEC en todo momento, y el resaltado indica *cuándo* está enganchado.
  - El **shift light no es un elemento aparte**: es el color del arco del tacómetro por delante de la aguja, según los umbrales de §7. Se decidió así para no gastar espacio de pantalla ni obligar a mover la mirada a otra zona.
- **Velocidad digital** grande, secundaria en jerarquía pero legible.
- **Temperatura de refrigerante** como barra con zonas normal y alta.
- **IAT, voltaje y carga** como valores pequeños en una fila inferior.

### 6.7 `DashActivity`

Mantiene la pantalla encendida, fullscreen inmersivo horizontal, tema día/noche, permisos Bluetooth (modelo antiguo y `BLUETOOTH_CONNECT` de Android 12 en adelante), y la selección del adaptador la primera vez, que se recuerda después.

## 7. Valores derivados

Constantes del F20C, centralizadas en un solo archivo (`EngineConstants.kt`) para ajustarlas fácil. Estos son los **valores que se implementan por defecto**; si el usuario los corrige, se cambia una línea. No son un pendiente que bloquee nada.

| Constante | Valor |
|---|---|
| Enganche del VTEC | 5850 rpm |
| Inicio de zona roja | 8300 rpm |
| Corte de combustible | 9000 rpm |
| Máximo del tacómetro | 9000 rpm |
| Umbral ámbar del shift light | 7500 rpm |

- `vtecActive` es `rpm >= 5850 && loadPct >= 60`. La carga importa: a bajo pedal el VTEC no engancha aunque las revoluciones estén arriba.
- `shiftLight` es verde por debajo de 7500, ámbar entre 7500 y 8300, rojo arriba de 8300, y parpadea cerca del corte.
- `sessionMaxRpm` es el máximo desde que arrancó la app.

Ninguno consume lecturas: los tres se derivan del RPM y la carga que ya se leen.

## 8. Interpolación de la aguja

**El detalle de UX más importante del proyecto.**

El RPM llega cada ~160 ms. Una aguja que salta cada 160 ms se ve descompuesta. La vista corre a **60 fps** y suaviza el valor mostrado hacia el objetivo con amortiguamiento exponencial, con constante de tiempo de ~120 ms, ajustable en una constante.

**Trade-off aceptado:** añade unos 100 ms de retraso percibido en la aguja. Es el intercambio correcto para un tablero, y no hay forma de rodear la física del K-line — la alternativa es una aguja escalonada.

## 9. Máquina de estados de conexión

```
Disconnected ──► Connecting ──► Initializing ──► Polling
     ▲                │              │             │
     └────────────────┴──────────────┴─────────────┘
              (fallo / pérdida / motor apagado)
```

- **Reintento con backoff:** 1 s, 2 s, 4 s, 8 s, con máximo de 10 s.
- Al perder conexión se **conservan los últimos valores en gris**, no se borra la pantalla. Un tablero en blanco a media curva es peor que un dato viejo marcado como viejo.

## 10. Manejo de errores

**Regla dura:** cualquier respuesta no parseable se descarta como "sin muestra" y el scheduler continúa con el siguiente PID. Nunca se propaga una excepción a la UI.

Casos que el parser debe absorber sin fallar: `SEARCHING...`, `BUS INIT`, `BUS ERROR`, `STOPPED`, `NO DATA`, `?`, `UNABLE TO CONNECT`, cadena vacía, respuesta truncada a la mitad, y eco residual si `ATE0` no tomó efecto.

Tres timeouts consecutivos en el mismo PID marcan ese PID como no soportado y lo sacan de la rotación, liberando su presupuesto para el resto.

## 11. Estrategia de pruebas

| Unidad | Cómo se prueba |
|---|---|
| `PidDecoder` | Pruebas JVM puras, con cadenas reales y con toda la lista de basura de §10 |
| `Elm327Session` | Contra un transporte falso que reproduce respuestas guionadas, incluidos los fallos |
| `PollScheduler` | Verificar que las proporciones de consulta sobre N ciclos coincidan con §5 |
| `DashView` | Sin pruebas automatizadas — validación visual en el radio |

Las tres primeras corren en la JVM sin dispositivo. Esto importa porque **no queremos depurar dentro del carro**.

## 12. Riesgos abiertos

| ID | Riesgo | Mitigación |
|---|---|---|
| R1 | **Tipo de adaptador sin verificar.** Se asume SPP clásico; si es BLE, `SppTransport` no conecta. | La interfaz `ObdTransport` aísla el cambio a una sola unidad nueva. |
| R2 | **Specs del head unit desconocidas**, tanto versión de Android como resolución. | `minSdk 21`, layout relativo al viewport, permisos BT en ambos modelos. |
| R3 | **Sin ruta de instalación confirmada.** adb por USB no funciona (§13). | Tres alternativas en §13; ninguna bloquea el desarrollo. |
| R4 | **Sin modo demo, la UI no se puede verificar hasta tener el APK instalado en el radio y el carro encendido.** Decisión explícita del usuario. | Las pruebas JVM cubren protocolo y decodificación; el tacómetro se valida a ojo en el carro. |
| R5 | El AP1 podría no usar ISO 9141-2. | `ATDP` reporta el protocolo real y se cae a `ATSP0` automático. |

## 13. Instalación en el radio

**Hecho verificado:** `adb devices` no ve nada, y la enumeración USB de Windows no muestra ningún dispositivo Android. La causa más probable es que los head units exponen puertos USB-A **host**, no de periférico; un cable USB-A a USB-A une dos hosts y no enumera. Falta confirmar si el radio tiene un puerto micro-USB o USB-C de datos.

Tres vías, en orden de preferencia:

1. **adb sobre Wi-Fi** con `adb connect <ip>:5555`. Es la vía normal para head units y permite instalar e iterar rápido.
2. **Memoria USB**: copiar el APK y abrirlo con el explorador de archivos del radio.
3. **Link de descarga** desde el navegador del radio.

Se decide al llegar ahí. No bloquea nada anterior.
